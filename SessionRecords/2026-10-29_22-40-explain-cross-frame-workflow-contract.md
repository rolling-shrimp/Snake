## Summary

本次先恢復 2026-10-25 的 v1／v2 規格差異分析，再詳細釐清「v2 主要強化分解、命名、引用與可追溯性，但沒有同步補上跨 frame 的完整工作流程契約」的含義。

核心結論是：v2 能清楚描述許多局部 use case、規則 ID、acceptance scenario 與測試的對應關係，但沒有一份上層契約完整擁有一次 250ms 遊戲 tick。因而沒有統一規定各局部行為的執行順序、狀態版本、分支優先級、停止條件、原子結果與最終 invariant；實作者必須自行拼裝，造成每個局部測試都通過，整體玩家流程仍可能錯誤。

分解本身不是問題，也不代表應將所有程式寫進一個巨大方法。真正缺少的是一個對外部觸發到完整可見結果負責的 workflow／orchestration contract，內部仍可委派給各個小 use case 或 helper。

## Detailed Q&A Record

### Q1. 上次比較 v1 與 v2 得到什麼結論？

上次以 `origin/master` 作為 v1 比較來源，以目前工作樹的 `Domains/`、`misfit.yaml` 與 `Pattern Network/` 作為 v2 規格來源。v2 有大量 YAML、acceptance scenario、Pattern Gate 與追溯索引；問題不是規格檔案太少，而是契約邊界沒有對準玩家真正執行的一次完整操作。

v1 的 `AdvanceFirstLevelStep()`、`AdvanceSecondLevelStep()`、`AdvanceThirdLevelStep()` 契約以一次完整遊戲步進為粒度，串起移動、碰撞、物件效果、長度變化、護盾／死亡、過關、物件補充與狀態更新。v2 將同一流程拆成 `advance-snake-step`、碰撞 handler、食物 handler、`evaluate-level-completion`、`replenish-triggered-object`、read-model 更新與 Render 等局部行為，卻沒有另一份上層規格重新定義它們如何組成一次完整 tick。

上次確認現有測試與 Gate 均能通過，但它們主要證明「已寫下的 scenario 有對應測試」以及「結構、引用與依賴符合規則」，不能證明未寫入規格的重要邊界情境沒有遺漏。

### Q2. 「分解、命名、引用與可追溯性」各自在說什麼？

- **分解：** 將一次玩家可見的完整步進拆成移動、碰撞、食物效果、長度變化、護盾、關卡完成、物件補充、read model 與 Render 等較小 use case。
- **命名：** 每個 use case、規則、scenario 與 Gate 都有明確名稱或 ID，方便準確討論與定位。
- **引用：** 記錄 acceptance 屬於哪個 use case、presentation 關聯哪個 Domain、Gate 驗證哪個結構，以及規格與測試之間的關係。
- **可追溯性：** 能從規則追到 scenario、測試或程式結構，確認已宣告的規格項目是否有落點。

這些能力主要回答「有哪些零件、零件叫什麼、互相引用誰、已宣告的項目是否有測試」，但不自動回答「所有零件在一次完整操作中如何協作」。可追溯性只能證明已列出的 scenario 被追蹤，不能證明所有必要 scenario 都已列出。

可用地圖類比：所有已畫出的道路都有名稱、編號與連接資料，不代表地圖沒有漏掉一座必要的橋。尾格碰撞、蛇身拓樸、完整 tick 順序、連續 UI 更新與實體按鍵映射，就是可能未被畫入地圖的部分。

### Q3. 這裡的「frame」與「跨 frame」是什麼？

此處的 frame 不是畫面 FPS 的影格，而是 Pattern Network／Use Case 中切分出的個別行為單元，例如：

- `advance-snake-step`
- `handle-self-collision`
- `handle-ordinary-food-contact`
- `evaluate-level-completion`
- `replenish-triggered-object`
- `update-level-status-read-model`

「跨 frame」指的是這些局部行為之間的共同語意，包括誰先誰後、上一階段交給下一階段什麼資料、哪些分支互斥、何時停止後續流程，以及何時才可公開最終結果。

### Q4. 完整工作流程契約應該回答哪些問題？

一次 250ms tick 的概念流程可能是：

```text
Timer 觸發已到期的 tick
        ↓
確認遊戲是否為 Playing
        ↓
套用本次有效方向
        ↓
計算下一個蛇頭位置
        ↓
依本步尾巴是否離開判斷碰撞
        ↓
處理物件效果與蛇身變化
        ↓
處理護盾、死亡或過關
        ↓
補充需要重新產生的物件
        ↓
建立完整 read model
        ↓
一次公開最終畫面
```

這只是用來說明契約需要涵蓋的範圍；真正的執行順序仍應由正式規格決定。完整契約至少要定義：

1. **契約擁有者：** 哪個工作流程入口對一次完整 tick 負責，而不是讓 Timer callback 或 Presenter 自行拼裝局部 use case。
2. **輸入與輸出粒度：** 輸入是一次已到期 tick 與所需遊戲狀態；輸出是一次完整處理後的單一結果。
3. **固定順序：** 碰撞、移動、食物、長度、護盾、死亡、過關、補物件與 read-model 更新的先後關係。
4. **狀態版本：** 每一步看到的是移動前、計算中、效果處理後，還是最終提交的狀態。
5. **分支互斥與優先級：** 撞牆、自撞、護盾、死亡與過關能否同時成立，以及哪個結果優先。
6. **停止條件：** 發生死亡、救援或過關後，哪些後續步驟不得再執行。
7. **原子可見性：** 玩家只能看到 tick 前與 tick 後的完整狀態，不能看到分數、物件、關卡狀態分批更新的中間結果。
8. **整體 postcondition／invariant：** tick 完成後蛇身拓樸、長度、物件位置、關卡狀態與畫面資料必須彼此一致。

### Q5. 尾格碰撞為什麼能說明跨 frame 契約的缺口？

假設蛇頭下一步要進入目前尾巴所在格。若只看移動前的 `body_cells`，該格確實被蛇身占用，局部規則可能直接產生 `SelfCollision`。

但如果本次是普通移動，尾巴會在同一步離開，蛇頭進入即將空出的尾格可能合法；如果本步需要保留尾巴，該格仍會被占用，則可能構成碰撞。因此真正的判斷不是單純的：

```text
下一格是否存在於目前 body_cells？
```

而是：

```text
依本次完整 tick 的移動與長度語意，
蛇頭進入下一格時，該格是否仍被蛇身占用？
```

這個判斷同時需要下一位置、碰撞、移動、尾巴是否移除與長度變化等局部行為的資訊。若沒有上層契約，碰撞 handler 不知道應使用哪個時間點的蛇身，也不知道尾巴在本步是否會離開。不同實作者可能採用不同順序，而且都能滿足目前較局部的規格。

### Q6. 為什麼各局部測試通過，整體仍可能錯？

例如三個局部測試分別證明：

- 移動後蛇頭前進一格；
- 吃到食物後蛇身數量增加一格；
- Playing 畫面最後包含棋盤、分數與規則說明。

它們仍不能排除以下問題：

- 新增的蛇身格出現在遠方合法空格，而不是從尾端連續延伸；
- 移動、成長與狀態更新各 Render 一次，使玩家看到中間狀態；
- 每次 Render 都清除並重建規則控制項而產生閃爍；
- 蛇身數量正確，但 body cells 不構成連續有序路徑；
- 同一 tick 先產生死亡，後續又產生過關或補物件結果。

每個局部斷言都可能成立，但沒有測試從一次 tick 的輸入一路驗證到最終可見結果。這就是「局部正確不代表工作流程正確」。

### Q7. 補完整流程契約是否等於寫一個巨大方法？

不是。規格上的完整契約與程式中的單一巨大方法是兩件事。

工作流程入口可以負責一次完整 use case，並將碰撞、物件效果、狀態轉換等工作委派給小型且責任清楚的協作者。重點是上層契約仍要擁有完整順序、分支與最終結果，不能因內部拆分就把整體語意交給實作者臨場決定。

v1 相對不容易出現這類問題，不是因為規格少或所有程式都應集中，而是其 `Advance...Step()` 契約仍以玩家的一次完整步進為邊界。v2 提升局部規格精度後，沒有保留同等層級的整體契約。

## Key Clarifications

- 此處的 frame 指局部 use case／行為單元，不是 UI 的畫面影格。
- 問題不在於拆分 use case；問題在拆分後缺少一個重新組合並擁有完整結果的契約。
- 有 scenario ID、測試與引用只證明已宣告內容可追溯，不證明需求或邊界情境完整。
- 完整 workflow contract 需要定義順序、資料狀態、互斥分支、停止條件、原子可見性與整體 invariant。
- 完整契約不要求巨大方法；內部仍可分解，但外部必須有一個入口對整次玩家操作負責。
- UI 閃爍也可能是同一類缺口：靜態畫面最終符合規格，不代表連續更新過程不會暴露中間狀態。
